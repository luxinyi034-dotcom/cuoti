## 1. 一条教训

为了让新版“打开是空的”，把数据存储的键名从 `app.v2` 换成了 `app-v9`。结果使用者在旧键里导入的内容，新版本读不到，看起来就是“全没了”。之后做了“找回”，但使用者想要的那一份已经在一次“找回”中被覆盖了，最终没找回来。

教训：**想让界面从空白开始，就去掉预设内容；绝不换存储位置。**任何会覆盖数据的操作，执行前先备份。

## 2. 存储的规则和代码模式（以 localStorage 为例，其他存储同理）

```js
const DATA_KEY = 'myapp-data';        // 所有版本共用，永远不改
const APP_VERSION = 'v12';

let RAW_AT_LOAD = null;
function load() {
  try { RAW_AT_LOAD = localStorage.getItem(DATA_KEY); } catch (e) {}
  if (RAW_AT_LOAD) {
    try {
      const r = JSON.parse(RAW_AT_LOAD);
      if (r && r.v === 2) return migrate(Object.assign(defaults(), r));  // 只增不删
    } catch (e) {}
    // 读不懂：原样另存，绝不覆盖
    try { localStorage.setItem(DATA_KEY + '.rescue.' + Date.now(), RAW_AT_LOAD); } catch (e) {}
  }
  return defaults();
}

function save() {
  const str = JSON.stringify(S);
  for (let i = 0; i < 30; i++) {
    try { localStorage.setItem(DATA_KEY, str); return true; }
    catch (e) { if (!dropOldestSnapshot()) break; }   // 空间不够先腾出最旧的备份
  }
  warnUser('存储空间不够，刚才的改动没有保存，请导出备份');  // 绝不悄悄失败
  return false;
}
```

- `migrate()` 里只做“补上新字段的默认值”“把旧结构转换成新结构”，不删除使用者的任何内容。
- 判断“今天”之类依赖时间的逻辑，所有地方用同一个函数（例如学习日从凌晨 4 点开始时，`dayStart()`、`dayKey()` 统一处理），避免两个页面算出不同结果。

## 3. 自动备份

- 时机：换到新版本时（用打开那一刻读到的原始数据）、每天第一次打开、任何覆盖或清空数据的操作之前（恢复、导入备份、清空、找回……）。
- 和最新一份完全一样就不重复存；按数量和总大小保留（如每天的留 7 份、其他留 8 份、总量约 2.5M 字符，最新两份总是留着）。
- 设置里列出每份备份：时间、原因、版本、内容摘要（几个话题、几张卡、打卡几天），“恢复”要点两次确认；恢复前先备份当前数据。
- “这台设备上的数据”：列出所有存储位置各有多少内容，能展开看具体有什么，帮使用者判断数据在哪。
- 导出 / 导入备份文件（.json）；N 天没导出就在首页提醒一次，可以“过几天再说”。
- 跟使用者说清楚：主屏幕上的 Web App 和浏览器里的网页存储是分开的；自动备份和 App 数据在一起，防不了浏览器清除数据，所以要导出。

## 4. 测试数据和正式数据分开

- 正式版不带任何演示内容；演示内容（示例话题、示例笔记）只打进测试台。
- 测试台用自己的存储键，可以模拟日期、一键造出各种场景（比如“考前第 3 天”“有 3 个到期的复习”）。
- 测试台入口藏在设置最底下，平时用不到。

## 5. 版本发布的结构

```
站点/
  index.html        最新版（主地址，添加到主屏幕用这个）
  sw.js             离线缓存，缓存名带版本号，页面走“先联网”
  manifest.webmanifest, icons/
  v10/index.html    存档：旧版本预览（用数据副本，顶部提示“回到最新版”）
  v11/index.html
```

- 发布脚本做三件事并自我检查：版本号和 changelog 第一项一致；数据键没被改；这个版本的存档目录不存在（存在就拒绝发布，绝不覆盖）。
- 存档页面：启动时把正式数据复制到一个预览键里，只读写预览键；不做自动备份、不提示找回。
- App 设置里显示“当前版本 vN、这一版改了什么、以前的版本（链接到存档）”。

## 6. 升级测试（每次发布前）

1. 用发布脚本把新版本发布到一个**临时**站点目录（不是真正的线上目录）。
2. 把线上正在用的上一版页面放到同一个临时站点下（同源，才能共用存储）。
3. 在上一版里导入真实格式的内容、造学习进度和打卡记录。
4. 打开新版本，检查：内容、进度、打卡全在；有“升级到 vN 之前”的自动备份且和升级前一字不差；恢复备份可用且可撤销；旧版本预览改不到真正的数据；损坏的数据被另存；存储满了不悄悄丢。
5. 全部通过才发布到线上。把这个测试脚本放进项目仓库（如 `tests/upgrade.mjs`），版本号从代码里读，以后每次直接跑。

## 7. 发布清单

- [ ] 改版本号和 changelog（第一项写这一版改了什么，用使用者的话）
- [ ] PRD 写好这一部分（含验收标准）
- [ ] 新功能 / 修复都有自动测试；以前的测试全部通过
- [ ] 截图自查（使用者的设备尺寸）
- [ ] 升级测试通过
- [ ] 提交源码（先拉取远端，有别人的改动就合并、不覆盖）
- [ ] 发布到站点、确认部署成功
- [ ] 汇报：结果、改了什么、数据安全、验证了什么 / 没验证什么
