## 1. 拆解零碎的需求

使用者常用语音输入，句子长、口语、会重复、偶尔没说完。处理方法：

1. 找出每一件**独立要改的事**，编号。
2. 每件事想清楚“使用者看到的现象”和“真正的需求”。比如“它只能是查看，并不能更改”→ 真正需求是“自己选今天学哪个话题”。
3. 对照现在的实现，说出**为什么现在会这样**。很多“bug”其实是设计没考虑到的情况（话题少时合适的列表，话题多了变成一长串），说出原因能让使用者信任你的改法。
4. 给出**打算怎么改**，一两句，具体到界面上会出现什么。
5. 使用者附带的质量要求（“要美观”“不要逻辑混乱”）变成可检查的标准，写进待办 / PRD。

## 2. “先记住，先别做”：待办格式

写进仓库的 `docs/待办.md`，这样换个对话、换个人接手都不会丢：

```markdown
## 4. 范文默写：直接在文章里的空格里写（日期，来源：iPad 截图）

- 现状：文章里的空格只是显示位置，真正的输入框在文章下面，要翻下去写。
- 要改：点文章里的空格就在原地输入；写完回车检查；检查、提示、看答案在屏幕下方固定的操作条里。
- 页面要美观（使用者特别要求）：……
```

做完后在待办里标“已在 vN 完成，见 PRD 第 X 部分”。

## 3. 回复的结构

- 第一句直接回答 / 给结论。
- 然后按使用者的编号逐条：**原因**、**打算**（或**已改成**）。
- 涉及数据时单独一段说数据安不安全。
- 最后一句告诉使用者下一步（“还有别的继续说，说齐了我先画设计稿”），或问一个真正需要对方决定的问题。
- 用使用者的语言；语气平实，不夸张、不堆形容词；不说“完美”“全部搞定”这类话，有没验证到的要直说。

## 4. 真实例子

**使用者**：“首先就是今日新学里面，你不能选择自己要背哪个主题单词……一天最多只能学 1 个……第二个页面显示了那么多的主题单词？这是我不太明白的设计逻辑……你可以先把我说的问题记住，然后说一下你大概可以怎么改，但是就先不要去做网站。”

**好的回复要点**：
- 拆成 3 条：不能选话题 / 一天只能一组 / 今日学习列出全部话题。
- 第 3 条坦白：“那一长串原本就是让你在这里选话题的地方，话题少时还行，你现在有 12 个话题，就变成看不懂的一长串，这是我设计得不好。”
- 每条给打算；写进 `docs/待办.md`；结尾“还有别的继续告诉我，说齐了先画设计稿，再统一做成新版”。不动代码。

**使用者**：“然后就是我在切换论点比如说我在默写的时候切换论点请你一定要确保我的默写记录不要”（没说完）

**好的回复**：“你的消息好像没打完，我理解为‘默写记录不要丢’，已经记成第 8 条：……如果你想说的不是这个意思，告诉我我再改。”

**使用者**：“这里出现了一个 bug……我已经完成了任务，它还是让我继续挑选新的一组……使两个页面统一一下。”（截图时间是凌晨 1:23）

**好的处理**：从截图里的细节（打卡在周六、时间凌晨）推断出根因——这一组前一天晚上开始、过了午夜才学完，“组”按开始时间算、“打卡”按结束时间算，两处不一致。先写测试复现，再修成同一个规则，并让老数据也按新规则算对；回复里讲清原因，再顺势问一个有价值的问题：“要不要把一天的分界改成凌晨 4 点？”

## 5. 出了问题时

- 先止损：不再做任何会覆盖数据的操作。
- 说清楚发生了什么、是谁的原因（是自己的改动导致的就直说并道歉），不推给使用者。
- 给出能做的补救，并把“以后怎么避免”落实成规则（写进 CLAUDE.md），而不是只做口头保证。
- 不能保证的事（比如设备上的数据被浏览器清除）要如实说明，并给出对应的保护办法（导出备份）。
