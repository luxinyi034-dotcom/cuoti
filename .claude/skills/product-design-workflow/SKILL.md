# 设计驱动的 App 开发流程

这套流程来自一次很成功的长期合作（一个 iPad 上用的雅思写作学习 App，从 v1 做到 v13）。使用者对结果满意的地方，归结起来是五件事：

1. **方向不跑偏**：给了参考图，做出来的大方向就对。
2. **数据不丢**：每次更新数据都在，版本更新的方式是使用者想要的。
3. **听得懂**：使用者说得零碎、口语、甚至没说完，也能准确抓住要改什么。
4. **流程稳**：大改动先出设计稿确认，再写 PRD，再做；后面怎么改都不乱。
5. **风格统一又好看**：新功能一直符合整个 App 的设计风格。

下面每一节讲怎么做到，以及为什么。细节放在 `references/` 里，用到时再读。

## 0. 先判断这次是哪种活

| 使用者的话 | 做什么 |
|---|---|
| 给了参考图 / 描述了想要的样子，要新做一块 | 第 1 节 → 第 3 节完整流程 |
| 一串修改意见，但说“先记住”“先别做” | 第 2 节：记进待办，逐条说原因和打算，不动代码 |
| “可以”“就这样”（确认设计稿或方案） | 写 PRD → 实现 → 发布 |
| “直接做一个新版给我” | 跳过设计稿，但照样写 PRD、照样截图自查、照样按版本发布 |
| 报 bug（常带截图） | 先复现、找到根因、说清楚为什么，再修；修完发新版本 |
| 担心数据 / 数据丢了 | 第 4 节，先止损（不要再覆盖任何东西），再找回 |

## 1. 读懂参考，定下风格（方向不跑偏的关键）

使用者给的参考图是“意思”，不是要照抄的像素。先提炼出一份**风格说明**，写进 PRD 开头，后面所有界面都对照它：

- 颜色：一套主色系（例如 sage 绿 + 米色 + 少量强调色），写成 CSS 变量（`--sage`、`--paper`、`--ink`、`--line`……），所有组件只用变量。
- 字体：标题 / 正文 / 英文 / 数字各用什么，字号层级。
- 密度和形状：圆角、边框粗细、卡片阴影、留白、行距。
- 区分不同类别时**用图标 + 名称，不用不同颜色**——颜色一多就乱，统一色系是“高级感”的来源。

然后做**设计稿画布**：一个可以打开看的页面，每张设计稿有编号（A、B、C… 或 AA、AB…），按排分组。

- 大的决定给 2–3 个方案并排，写清每个方案的取舍，让使用者选；选定后在 PRD 里写“选定 BW”。
- 设计稿里用**真实的内容**（真实的单词、段落、长短不一的数据），不要用“示例文字”。好不好看要在真实内容下判断，比如答案很长时会不会撑乱排版。
- 设计稿要包括各种状态：空的、进行中、写对、写错、内容特别长、手机竖屏。
- 被否掉或改过的设计稿**替换掉**，不要越堆越多。

详见 `references/design-and-style.md`。

## 2. 听懂使用者（让对方觉得“你懂我”）

使用者常常边想边说，一条消息里有好几件事，有时没说完就发出来了。

- **逐条拆开、编号复述**：“你说的是这 3 件事：1… 2… 3…”。每条写**现在为什么会这样（原因）**和**打算怎么改**。说原因很重要：使用者常把设计问题当成 bug，或把 bug 当成设计；先讲清楚原因，对方才能判断改法对不对。
- **“先记住、先别做”**：把每条写进仓库里的 `docs/待办.md`（换个对话也不会忘），回复里逐条说原因和打算，然后停下。等使用者说“可以 / 直接做”再统一做成一个新版本。
- **消息没说完**：按最合理的意思理解并明说“你的消息好像没打完，我理解为……”，照这个记下来，请对方纠正。不要干等。
- **使用者追加的要求**（比如“做大的时候要保证整个页面美观”）要落实成具体、可检查的标准写进待办和 PRD，而不是只回一句“好的”。
- **用使用者的语言回复**，少用术语；需要用时顺手解释。回复用短段落和编号，和使用者列问题的编号对应。
- 确实需要使用者拍板的事（命名、要不要某个功能、在两种行为里选一种）再问；能从上下文、代码、常识判断的就直接定，并在回复里说一句。

详见 `references/communication.md`（含这次合作里的真实例子）。

## 3. 设计稿 → PRD → 实现 → 截图自查

**为什么要这样排**：设计稿让使用者在花工夫之前就看到结果；PRD 把确认过的东西写成规则，后面改别的地方时有依据，不会把以前定好的推翻；实现时照着 PRD 做，验收时照着 PRD 的验收标准查。这就是“后面再怎么改也不跑偏”的原因。

1. **设计稿**（大的界面改动）：见第 1 节。发给使用者确认，问清有异议的地方。
2. **PRD**：一个持续更新的文档（例如 `docs/PRD-v3.md`），按“部分 → 节”编号，每部分写：
   - 适用版本、对应的设计稿编号；
   - 规则（用使用者能看懂的话写，包括边界情况：空的时候、内容很多时、手机上）；
   - 数据要求（新加了哪些字段，旧数据怎么转换）；
   - 验收标准（编号列出，能逐条检查）。
   PRD 开头的“状态”行写清已确认到第几部分。
3. **实现**：复用已有的组件和样式变量，新东西长得像老东西。
4. **截图自查**：用浏览器自动化（如 Playwright）在**使用者实际用的设备尺寸**上截图——这次是 iPad 横屏 1180×820、竖屏 820×1180、手机 390×844——自己看一遍：对齐、行距、留白、有没有被遮住、长内容会不会撑破。发现问题先改再交付。只看测试通过不够，好不好看要看图。
5. **自动测试**：每个新功能、每个修过的 bug 都留一个测试脚本（重现使用者的真实场景，比如“晚上 23:50 开始、00:30 学完”）；连同以前的测试一起跑，全部通过才发布。

## 4. 数据：一条都不能丢（最重要）

这次合作里有过一次教训：为了让新版本“从空白开始”，把数据的存储位置换了，使用者之前导入的内容在新版本里就“消失”了，最后没能找回。从那以后定下的规则，适用于任何存用户数据的 App：

- **存储位置永远不变**：所有版本读写同一份数据。想让界面“从空白开始”，是不带预设内容，而不是换存储位置。
- **只增不删**：新版本只加字段；结构要变就写迁移，把旧数据转换过去。
- **读不懂的数据不覆盖**，原样另存一份。
- **保存不能悄悄失败**：空间不够先腾出旧备份再试，还不行就明确提醒。
- **自动备份**：换新版本前、每天第一次打开、任何覆盖/清空数据的操作前，各存一份；设置里能看到、能一键恢复，恢复前也先备份（恢复错了还能恢复回去）。
- **导出提醒**：数据只在设备上时，定期提醒导出到云盘；告诉使用者自动备份防不了“设备上的数据被清除”。
- **测试数据和正式数据分开**：测试台、演示内容用另一份存储，绝不混进正式版。
- 把这些规则写进项目的 `CLAUDE.md`，以后任何人改这个项目都看得到（模板见 `assets/CLAUDE-template.md`）。

具体做法和代码模式见 `references/data-and-releases.md`。

## 5. 版本：主地址永远最新，旧版本都留着

- **主地址永远是最新版**：使用者只把主地址添加到主屏幕一次，以后更新自动出现在同一个图标里。
- **每次更新一个新版本号**（v10、v11……），每个版本另存一份存档地址（`/v11/`），打开存档是“旧版本预览”，用数据的副本，在里面操作不影响真正的记录。**已经发布的版本绝不覆盖。**
- 版本号和“这一版改了什么”只写在一个地方（如 `changelog.json`），App 设置里显示当前版本和更新内容。
- **发布前必做升级测试**：拿线上正在用的上一版构建，造出带内容、进度、打卡的数据，再用新版本打开，确认全都在、并且有“升级到 vN 之前”的自动备份。通过了才发布。
- 发布后确认部署成功；自己打不开线上网址时要如实说“没能亲眼确认线上页面”。
- 发现另一个会话也改了同一个仓库：合并，不要覆盖别人的改动，并告诉使用者。

## 6. 交付时怎么汇报

使用者想知道四件事，按这个顺序说，简短：

1. **结果**：做好了吗、网址、怎么更新（“关掉 App 再打开”）。
2. **改了什么**：按使用者提问题时的编号逐条对应，用使用者的话说。
3. **数据安全**：数据都在、升级前自动备份了什么、旧版本在哪。
4. **验证了什么、没验证什么**：测试和截图检查了哪些；哪些没法亲眼确认要直说。

如果这次跳过了设计稿（使用者要求直接做），说一句并邀请截图反馈。最后可以问一个真正有用的后续问题（比如“要不要把一天的分界改成凌晨 4 点？”），不要堆一串选项。
