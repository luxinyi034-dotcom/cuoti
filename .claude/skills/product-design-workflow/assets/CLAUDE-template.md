# <项目名>：改动和发布规则

使用者最在意的是**数据一条都不能丢**。任何改动、任何发布都必须遵守下面的规则。

## 数据
- 所有版本读写同一份数据：存储键 `<DATA_KEY>`。**永远不改这个键**，也不新开别的键存正式数据。
- 新版本只能在旧数据上增加字段；结构要变就在 `load()` 之后写迁移，不能删掉使用者的内容、进度和设置。
- 读不懂的数据原样另存（`.rescue.<时间>`），绝不直接覆盖。
- `save()` 不能悄悄失败：空间不够先删最旧的自动备份再试，还是不行要提醒使用者。
- 任何会覆盖或清空数据的操作，执行前先自动备份。
- 测试 / 演示数据用另一个存储键，不混进正式版。

## 发布
- 主地址 <URL> 永远是最新版；`<版本号>/` 是那一版的存档（旧版本预览，用数据副本）。
- 每次更新都是新版本号：先改版本号和 `changelog.json`，再运行发布脚本。已经发布的版本不能覆盖。
- 发布前必须跑升级测试（`tests/upgrade.mjs`）：用线上的上一版造数据，新版本打开后全部还在，并有“升级到 vN 之前”的自动备份。通过才能发布。

## 流程
- 大的界面改动：先画设计稿（画布 <链接>）给使用者确认，再写进 `docs/PRD.md`，然后实现，最后在使用者的设备尺寸上截图自查。
- 使用者说“先记住”的问题写进 `docs/待办.md`。
- 风格：<一句话风格说明，例如“统一用 sage 色系，类别用图标 + 名称区分，不用不同颜色”>。
- 回复用 <使用者的语言>。
